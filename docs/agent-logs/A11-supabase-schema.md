# A11 Supabase 스키마와 권한 검증

`feature/supabase-schema`에서 작성했습니다. SQL Editor에 붙여 넣을 파일은 [schema.sql](../../supabase/schema.sql) 하나입니다. [설정 안내](../../supabase/README.md)에 초보자용 프로젝트 생성부터 배포 후 확인까지 정리했습니다.

## 요구사항별 구현

| 요구사항 | DB에서 적용하고 확인한 내용 |
|---|---|
| AU-01·02·04 | 가입 트리거가 내부 도메인과 소문자 영숫자 4~20자를 검사합니다. 표시 아이디가 키와 일치하면 대소문자를 보존하고, 다르면 이메일의 키를 사용합니다. 중복 가입은 전체가 취소됩니다. 프로필은 본인만 조회합니다. |
| SH-01~03 | 메뉴 23종의 이름·가격·온도를 원본과 대조했습니다. 장바구니는 본인만 조회·삭제하고, 세 RPC가 온도와 수량을 검증합니다. 합산은 20개로 제한하며 합치기 배열의 한 항목이라도 실패하면 기존 수량이 유지됩니다. |
| SH-04~08 | 수령·결제 네 조합, 결제 상태, 한국 날짜 주문 번호, 주문별 총액을 검사했습니다. 잠근 행의 메뉴를 다시 확인하고 DB 단가·이름을 명세에 복사합니다. 빈 카트와 재결제는 거절됩니다. 명세 삽입에 실패를 주입해 주문·명세·카트가 함께 복구되는 것도 확인했습니다. |
| RV-01·03·04·06·07 | 본인 주문에서 실제 구매한 메뉴만 작성할 수 있고 주문·메뉴 조합은 유일합니다. 별점, 공백을 뺀 본문 길이, 사진 폴더와 쓰기 가능한 열을 제한합니다. 수정 시각은 트리거가 기록합니다. |
| RV-02·05·08·09 | 공개 목록은 지정된 열만 반환하고 작성자 끝 두 자리를 가립니다. 비회원과 다른 회원의 조회에서는 주문 ID가 비어 있습니다. 메뉴·내 리뷰 필터, 세 정렬 방식, 기본 정렬과 동률 순서를 검사했습니다. 리뷰 시드는 없습니다. 평균 표시는 프런트엔드 범위입니다. |
| §2 권한·저장소 | 앱 테이블 6개 모두 RLS를 적용했습니다. 테이블·시퀀스·함수의 권한을 거두고 필요한 작업만 허용합니다. 다섯 RPC와 가입 트리거의 권한 및 검색 경로를 검사했습니다. 공개 사진 버킷은 2 MiB와 세 MIME 유형으로 설정하며, 목록·추가·삭제는 해당 버킷의 본인 폴더로 제한합니다. |

`merge_cart(p_items)`의 JSON 키는 `menu_id`, `temperature`, `quantity`이며 디저트 온도는 빈 문자열입니다. [SQL 테스트](../../supabase/tests/schema.spec.ts)가 사용하는 [서비스 모형](../../supabase/tests/bootstrap.sql)은 운영 파일과 분리되어 있습니다.

SQL 검증은 같은 PGlite DB에서 스키마를 두 번 실행합니다. 두 실행 사이에 회원과 카트를 만들고 메뉴 가격을 바꿔, 두 번째 실행이 회원·카트를 보존하고 시드 가격을 복구하는지 확인했습니다. 각 클라이언트 쿼리는 독립 트랜잭션에서 JWT claims 모형과 `set local role`을 사용합니다.

루트 테스트의 공통 설정은 `window`와 `Element`에 접근합니다. 기존 설정을 유지하면서 루트 테스트 한 건이 Node 전용 Vitest 스위트 70건 전체를 실행하도록 연결했습니다. 첫 전체 실행에서 jsdom의 모듈 URL을 파일 경로로 변환하는 오류를 확인해 실행 경로를 수정했습니다. 최종 전체 실행에는 Three.js CommonJS 사용 중단 안내가 한 건 있었습니다.

## 실제 프로젝트에서 확인할 범위

- **Auth 및 AU-01·03·05~07** — 모형의 회원 삽입으로 트리거와 롤백을 확인했습니다. 실제 가입·로그인·로그아웃, 이메일 정규화·중복 응답, 메일 설정, 비밀번호 최소 길이·해싱, 세션 유지·갱신·만료, Auth 서비스 역할의 트리거 실행과 오류 전달은 호스팅 프로젝트에서 확인해야 합니다. 트리거는 평문 비밀번호를 받지 않습니다. 영숫자 입력 및 확인 입력 검사는 UI 소관입니다.
- **Storage 및 RV-07** — 버킷 메타데이터와 객체 행의 RLS를 검사했습니다. 실제 업로드 본문에 대한 MIME·크기 제한 집행, 이미지 리사이즈, HTTP 목록·삭제, 공개 URL과 캐시, 사진 교체·실패 후 파일 정리는 Storage 서비스와 브라우저가 필요합니다.
- **PostgREST** — SQL 역할별 접근은 검증했습니다. 공개 키·JWT 검증, 실제 요청에 대한 역할 및 claims 설정, 노출 스키마·스키마 캐시, RPC 매개변수 바인딩, 관계 포함 조회, 열별 쓰기와 반환, 오류의 HTTP 상태·클라이언트 매핑은 실제 API 검증 대상입니다.
- **동시성** — PGlite는 단일 연결입니다. 주문 재시도와 실패 시 원자성은 확인했으며, 독립 세션 두 개의 동시 결제 및 그 사이에 담기·수정·삭제가 겹치는 잠금 대기는 다중 연결 PostgreSQL에서 확인해야 합니다.
- **배포 및 화면 흐름** — 대시보드 조작, 프로젝트 일시정지·복원, 실제 관리 스키마의 기존 정책·권한, 환경 변수 주입과 Vercel 재배포를 실행하지 않았습니다. 모의 결제 창 승인·취소, 주문 내역 UI, 리뷰 사진 표시와 삭제 확인 등의 E2E는 통합 작업 범위입니다.

## Requests to orchestrator

- 공개 리뷰에 독립적인 `user_id` 열이나 원본 로그인 아이디 열은 없습니다. 다만 §2의 사진 경로가 `<auth.uid()>/<파일명>`이므로 사진을 첨부하면 공개 `photo_path`와 사진 URL에는 작성자 UUID가 포함됩니다. UUID를 경로에서도 숨겨야 한다면 저장 경로와 공개 URL 계약을 함께 조정해야 합니다.
- 실제 Supabase 프로젝트가 준비되면 위 Auth·Storage·PostgREST 연결과 두 세션 동시 주문을 확인해 주세요.
